# ADR-0032 — LinkedIn result post: one game page GET, `updateGameState` writes to one path, manual and opt-in

Date: 2026-11-15 · Status: accepted · Source: `.scratch/linkedin-submit/spec.md` (A1–A17 and its assumed lines), research 03 (HAR capture of the web client) · Amends ADR-0028 §1 (reads are GET only, never write to LinkedIn). Relates to ADR-0022 (release flags), ADR-0009 (P10, P12). Amended 2026-11-16 by research 03 Addendum 4 (unsolved-daily capture): a first-move write precedes the win. Amended 2026-11-17 by research 03 Addendum 8 (Mini Sudoku daily capture): a game LinkedIn still saves over voyager posts over a second write wire (§11).

## Context
ADR-0028 lets PuzzleBox read the player's own LinkedIn result and their connections' boards, and forbids any write. A player who solves today's LinkedIn daily in PuzzleBox still has no LinkedIn result: their LinkedIn streak breaks and their connections see nothing. The player asked for an opt-in way to post that solve.

A capture of LinkedIn's web client (research 03) showed that today's web app does not use the legacy voyager `update-game-state` mutation. A solve is POSTs to `/flagship-web/rsc-action/actions/server-request?sduiid=updateGameState`: a first-move call a moment after the page loads, then the win call. Each has a JSON body that echoes the board's server-issued state (puzzle id, profile id, request time, play counts) plus the game's play record. The game page itself is a plain `GET /flagship-web/games/<game>` that carries that initial state. The unsolved daily capture shows both calls with the same envelope and the same state keys; only the win state (`gameBoardHasWon`, time, path, backtracks, flawless flags) differs. A write returns 200 with `errors: []` and the existing voyager read then reports the game as solved, so a write lands in the record our reads already see.

Posting is a larger breach of LinkedIn's terms than reading: it is visible to the player's connections, it may count toward their streak or create a feed post (A14), and it cannot be undone. The posture must be stricter than the read posture, and the new wires must be few and pinned.

## Decision
1. **Two new wires on the account session, and no more.** ADR-0028 §1 now allows, besides the voyager reads and the photo exception:
   - **the game page GET:** `GET flagship-web/games/<game>`, once per post attempt. Its body is capped at 1 MB, parsed in memory for the server-issued state and never persisted. It is classified like a read; a page missing any required state key is `Rejected(Unexpected)` and no write follows;
   - **the write path:** `POST flagship-web/rsc-action/actions/server-request` with `@Query("sduiid") = "updateGameState"`. It is called twice per post, as the web client does: the first move, then the win. A game with no first-move play is a single win call.

   Nothing else on the account session may write, apart from the voyager save of §11: no other path, no further POST, no hand-built request.
2. **Manual, opt-in, experimental.** A post happens only on a tap of "Post to LinkedIn" on the result page of a qualifying solve (spec §2). It is behind a posting switch on the LinkedIn row in Profile → Accounts, labelled Experimental. The first turn-on shows a second risk warning that names the posting risks, and turning on requires accepting it. The consent time is persisted. Automatic posting is out of scope. The switch is separate from the connection (`LinkedInLink.posting`, never a field of `LinkState`) and resets to off on Disconnect.
3. **The port has one method per request.** `LinkedInResultPoster` in core/game's linkedin package, implemented in core/network, has `gamePage` and `send`, apart from `LinkedInAccountSource`. The flow reads through `gamePage(post)`, so the read goes over the wire the post's play saves through (§11); an `updateGameState` play reads the page GET of the post's route. `send` makes the first-move call and then the win call (§5). Each step of a post counts against the shared `LinkedInCallBudget` as its own slot (ADR-0028 §3 kept; the two writes of `send` share the one slot of that step), and the page checks (profile id, then tutorial, then puzzle id equals the solve's puzzle number, then already won) run in core/data against fakes. A tutorial page is checked before the puzzle id, because LinkedIn serves a new account its onboarding tutorial, with the tutorial's own puzzle id, in place of the daily. One tap sends up to four requests: the live own-result read, the page GET, the first move and the win.
4. **Never retries.** Each request is sent once. The post client is built like the account client: no cookie jar, no interceptor, no redirects, 10 s call timeout, the session read per request from `LinkedInSessionCookies` (ADR-0028 §2–3 unchanged). The client and the status → rejection table are shared with the account adapter, extracted once and never copied.
5. **Rejections pause; an unknown outcome does not.** The write has its own classifier. 200 with an RSC body whose `ServerRequestResponse` has `errors: []` is `Posted`. 409 is `AlreadyPlayed` and does not pause. 401/403, 429, 999 or a redirect, a non-empty `errors` and any other status are `Rejected` and trip the existing pause latch (ADR-0028 §4). A tutorial page is its own outcome, `Tutorial`: nothing is sent, nothing is paused and the post log is not touched, because LinkedIn is still onboarding the account and nothing is wrong with the link; like a day that is no longer today's, it is shown until the day's next tap or the end of the process. An I/O error or timeout *after* the request was written is `Unknown`: it may have landed, so it does not pause and the button asks the player to check (A16). A failure before the write is `Offline`, also without a pause. The first move is sent first, and only a clean `Posted` lets the win follow: any other outcome of the first move is returned as `send`'s outcome and the win is never sent. An I/O error after the first move was written is `Unknown` and likewise ends the send. The voyager save answers in another shape and reads a 409 differently; its classifier is §11's.
6. **A live check before the write.** Every post first makes a live own-result read, never the day sync's fetch-log cache. If LinkedIn already has a result, nothing is sent (A5). The next tap after an `Unknown` outcome checks first and never sends blindly.
7. **Single-flight, with a persisted sending marker.** A submit runs one at a time per (profile, game, day) in the app scope, so leaving the screen does not cancel it. A "sending" marker is persisted right before the write and cleared on a known outcome; a marker found at a later start reads as `Unknown`. The outcome is recorded after re-reading the link and dropped if the link changed. After LinkedIn's midnight (PT) an unposted result page no longer offers the button, and a tap on a page left open sends nothing (A17).
8. **The door refuses without consent.** The `LinkedInPush` release flag gated the two entries, the profile and result ViewModels, until Post to LinkedIn shipped in 0.35.0; the flag and its gates were then removed (ADR-0022 §5). The player's opt-in is the Experimental switch with its risk warning, and the data door `LinkedInPosts` refuses to post without posting consent, which only that switch can give.
9. **Konsist pins the wire.**
   - P10 keeps covering every production file of `:core:network` package `network.linkedin`. The one file named `LinkedInPostApi.kt` is exempt from its non-GET check alone; the client-leak checks still apply to every file.
   - P12 (`P12LinkedInPostPinnedWrites`, renamed from `P12LinkedInPostOnlyServerRequest` when it came to pin two POSTs) has the same subject set. A file named `LinkedInPostApi.kt` has exactly two non-GET annotations: `@POST("flagship-web/rsc-action/actions/server-request")` and, for §11, `@POST("voyager/api/graphql")`, one of each. No file in the package builds a write by hand (`.post(`, `.put(`, `.patch(`, `.delete(`, `.method(`).
   - A POST in any other file fails P10; a third, repeated or wrong POST path in `LinkedInPostApi.kt` and a hand-built write fail P12.
10. **A posted day never imports its own result.** The day sync reads LinkedIn's own result of a day this phone posted (decision 7's posted log) as read but writes no completion: that result is LinkedIn's copy of the player's PuzzleBox solve, and importing it would add a newer row with no replay. The shown solve of a daily stays its earliest solve, and the result page reads the replay of the stored row that is that solve.
11. **A game LinkedIn still saves over voyager posts over voyager.** Mini Sudoku is not on the SDUI page: LinkedIn's web client reads and saves it through voyager GraphQL (research 03, Addendum 8), so `updateGameState` cannot carry it. ADR-0028 §1 therefore allows one more write on the account session: `POST voyager/api/graphql` with `action=execute` and the persisted save query, called for the opening and again for the win. In place of the page GET it is preceded by one GET of today's game by game type, the persisted voyager query the Mini Sudoku feed already reads its puzzle with.
    - **The play picks the wire.** The game's encoder returns a `LinkedInPlay` whose `voyager` board is set, with no states and no payload keys. The post adapter sends a play that carries one over voyager and every other play over `updateGameState`. core/data does not know which game it is, and the order of a post (eligibility, live check, read, opening, win, post log) is the same on both wires. A wire flag on the daily source was rejected because a wrapping source forgets to forward it; a registry keyed by game path was rejected because the play is already the game's own data.
    - **The read.** The game is the `included` entry the response's first element names, and the member comes from its URN. The stored record's `gamePlayState` maps `UNKNOWN` to Fresh, `IN_PROGRESS` to Started and `END_SOLVED` to Won. A state not known here is Won, so nothing is sent over it, and a game with no readable stored record is `Rejected(Unexpected)`. The page checks of §3 then run unchanged.
    - **The save.** Each save is the member's whole stored record, keyed by the game URN of the page's member and the post's own game type and puzzle number: the cells the player filled (never a preset, never a note) ascending by index, the play state, the flaw flags and the time in whole seconds, rounded down and never below one. The opening is the board after the first digit, in progress and with no flaw, at the time that digit was placed; the web client's later autosaves are not replayed. Only the opening carries `includeWebMetadata`, as captured. A page that is Started gets the win alone.
    - **Headers.** The save sends the capture's headers whose values are known: its own `accept` (`application/vnd.linkedin.normalized+json`, not the `+2.1` of the reads), `origin` of LinkedIn's web client, the `x-li-track` the `updateGameState` write sends (the device's timezone and constants of the captured web client), the JSON content type, and the protocol and language headers the voyager reads send. The capture's page-instance and PEM header values are redacted, so those two are left out, not made up. The reads of this wire keep the headers of the account reads.
    - **Outcomes.** 200 whose body carries `data.data.updateIdentityDashGames` is `Posted`; any other 200 is `Rejected(Unexpected)`; every other status follows the shared table. On this wire a 409 says the stored record moved on under the save, not that a result exists, so the adapter reads the game once more inside the send's slot: a won record of the same puzzle is `AlreadyPlayed`, any other record is `Rejected(Unexpected)`, and a re-read that fails answers as that read (`Offline` when the network died, since the refused save left nothing behind). The save is not sent again. `Unknown` and `Offline` are as in §5, and so is the rule that only a `Posted` opening lets the win follow.
    - **Deletable.** `LinkedInPlay.voyager`, the voyager save with its body builder, reader and classifier, and the second pinned POST exist only for a game on this wire. When LinkedIn moves Mini Sudoku to `updateGameState`, its encoder returns states and payload keys and all of that is removed.

## Consequences
- LinkedIn will show a posted result under the player's name, to whoever LinkedIn's own settings allow. PuzzleBox never changes those settings (A7).
- A post is not undoable. The player's account may be restricted by LinkedIn; the switch, the first-use warning and the Experimental label say so.
- Live LinkedIn behavior (whether the server requires the first-move call or the trace and instance `x-li-*` headers, which stay omitted since made-up values are worse than none; the `x-li-track` header carries the device's timezone and constants of the captured web client) is outside CI. It rests on redacted recorded captures and a device probe, and drift lands in the pause latch, never in a retry loop.
- The page says how far the board got: Fresh (no saved play), Started (an accepted non-final save: `mostRecentGameState` holds the partial board, the time is the save floored to the second, plays are one higher and wins unchanged) or Won (an explicit won state, a complete saved play, or a saved play of a kind the reader does not know). Fresh sends the first move and then the win; Started sends the win alone, as the web client does after a reload; Won sends nothing. For Zip a saved trail is complete when it has `gridSize` squared cells.
- LinkedIn sometimes answers a save with 200 and a non-empty `errors` (a `ServerError` "Failed to update game state", `isRetryable: false`); a capture showed it transient. It stays `Rejected` and pauses the link, which is the conservative choice.
- A race with another device between the live check and the write is an accepted residual risk. LinkedIn's stored result is the truth; there is no read-back request after a post.
- Server-issued page state is used once and never stored, so there is no migration. Posted state and the consent time live in the device-only link prefs, which backup already excludes (A11).
- P12 is text-based: a write built without those method names (a reflection call, a `Request` made in another package) is not caught. The runtime tests of the post adapter (request count, method and path assertions) are the other half of the guarantee.
- The voyager wire rests on one redacted capture of a solve with no flaw. LinkedIn's own in-progress and solved reads of the game, a 409 and a 200 that carries GraphQL errors were not captured: the two reads are derived from the unplayed one, the 409 handling follows the web client's bundle (research 01), and an error 200 is `Rejected(Unexpected)`. A missing header LinkedIn turns out to require, or any other drift, lands in the pause latch.

## Rejected
- **The voyager save for a game that is on `updateGameState`.** The web client no longer uses it for Zip, Tango or Queens. It is used only for a game LinkedIn still saves that way (§11).
- **Posting automatically after a solve.** The breach is visible and irreversible, so each post is a player action behind a warning.
- **Extending `LinkedInAccountSource` with write methods.** The port would mix reads under the pause latch with a write that has its own outcomes, and the budget counts per request.
- **Keeping page state or the request time between attempts.** It is server-issued and short-lived; a stale value could post to the wrong day.
- **Allowing every non-GET in the package.** P10's value is that a new write fails the build; the exemption is one file and P12 pins that file to its two paths.
